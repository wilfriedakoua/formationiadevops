Ateliers pratiques

Six ateliers « papier + assistant », réalisables avec n'importe quel assistant IA autorisé par votre entreprise. Aucun cluster requis ; les commandes de validation sont fournies pour ceux qui disposent d'un environnement. L'atelier 6, plus long, fait la synthèse de la journée.

⚠️ Règle commune à tous les ateliersToutes les données fournies sont fictives. N'ajoutez aucune donnée réelle de votre entreprise (secrets, logs, noms de clients) dans les prompts.
Faire travailler en binômes (un « pilote » au clavier, un « relecteur » qui challenge l'IA), et inverser les rôles à chaque atelier. Debrief collectif de 5 minutes à la fin de chacun : « qu'est‑ce que l'IA a oublié ? »

1Du prompt vague au prompt pro ⏱ 20 min · M4

Objectif : mesurer concrètement l'effet d'un prompt structuré (R‑C‑C‑F‑A) sur la qualité d'un artefact.

Étape 1 — Le prompt naïf (3 min)

Fais-moi un Dockerfile pour mon API Python.

Envoyez‑le tel quel. Notez toutes les hypothèses que l'assistant a faites à votre place (version de Python, serveur, port, utilisateur…).

Étape 2 — Le prompt structuré (10 min)

Réécrivez la demande avec les 5 composants, à partir de ces informations :

  • Service catalog-api, Python 3.12, FastAPI servi par uvicorn, module app.main:app, port 8000.
  • Dépendances dans requirements.txt, code dans le dossier app/, santé sur /health.
  • Cible : Kubernetes. Exigences sécurité de l'entreprise : utilisateur non‑root, image minimale, pas de secret dans l'image.

Étape 3 — Comparer avec la grille (7 min)

CritèrePrompt naïfPrompt structuré
Image de base légère avec version précise (python:3.12-slim)☐☐
Build multi‑stage☐☐
Utilisateur non‑root (USER)☐☐
pip install --no-cache-dir☐☐
Ordre des COPY optimisé pour le cache (requirements avant le code)☐☐

Aucun secret / variable sensible en dur☐☐

Corrigé — exemple de prompt et de résultat attendu
RÔLE : Tu es ingénieur DevOps spécialisé en conteneurs sécurisés. CONTEXTE : Service catalog-api, Python 3.12, FastAPI servi par uvicorn (module app.main:app), port 8000, dépendances dans requirements.txt, code dans app/, endpoint de santé /health. Déployé sur Kubernetes. TÂCHE : Écris le Dockerfile de production. CONTRAINTES : - image de base python:3.12-slim, build multi-stage - utilisateur non-root avec UID fixe - aucune donnée sensible dans l'image, pas de cache pip - couches optimisées pour le cache de build FORMAT : le Dockerfile, puis un .dockerignore. Commentaires brefs en français. AUTO-REVUE : termine par la liste de tes hypothèses et 3 points à vérifier.
# syntax=docker/dockerfile:1
FROM python:3.12-slim AS builder
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir --prefix=/install -r requirements.txt

FROM python:3.12-slim
ENV PYTHONDONTWRITEBYTECODE=1 PYTHONUNBUFFERED=1
RUN useradd --create-home --uid 10001 appuser
WORKDIR /app
COPY --from=builder /install /usr/local
COPY --chown=10001:10001 app/ ./app
USER 10001
EXPOSE 8000
CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]

Points de debrief : un HEALTHCHECK Docker est inutile sur Kubernetes (ce sont les probes du Deployment qui comptent) ; le tag de l'image de base peut être épinglé par digest pour une reproductibilité totale ; scanner l'image avec trivy image avant publication.

2Générer puis durcir un déploiement Kubernetes ⏱ 25 min · M5

Objectif : pratiquer la boucle « générer → valider → durcir → documenter » et repérer les oublis par défaut de l'IA.

Étape 1 — Génération naïve (3 min)

Écris un Deployment Kubernetes pour mon service catalog-api qui se connecte à PostgreSQL.

Résultat typique observé :

apiVersion: apps/v1
kind: Deployment
metadata:
  name: catalog-api
spec:
  replicas: 1
  selector:
    matchLabels: { app: catalog-api }
  template:
    metadata:
      labels: { app: catalog-api }
    spec:
      containers:
        - name: catalog-api
          image: catalog-api:latest
          ports: [{ containerPort: 8000 }]
          env:
            - name: DATABASE_URL
              value: "postgresql://admin:SuperSecret@postgres:5432/catalog"

Étape 2 — Revue avec la checklist (7 min)

Relevez tous les problèmes. Puis demandez à l'IA : « Agis comme un auditeur sécurité Kubernetes et liste tous les problèmes de ce manifest, classés par gravité. » A‑t‑elle trouvé les mêmes que vous ?

  • ☐ Tag d'image immuable (pas latest), registry explicite
  • ☐ Namespace explicite
  • ☐ Plusieurs réplicas, stratégie de rolling update
  • ☐ readinessProbe et livenessProbe sur /health
  • ☐ requests / limits
  • ☐ Secret externalisé (secretKeyRef)
  • ☐ runAsNonRoot, allowPrivilegeEscalation: false
  • ☐ capabilities.drop: [ALL], FS racine en lecture seule
  • ☐ Labels standard app.kubernetes.io/*
  • ☐ automountServiceAccountToken: false si inutile

Étape 3 — Durcissement (10 min)

Rédigez un prompt R‑C‑C‑F‑A qui intègre les points de la checklist, puis faites durcir le manifest. Si vous avez un cluster ou kubeconform :

kubectl apply --dry-run=server -f deployment.yaml
kubeconform -strict -summary deployment.yaml

Étape 4 — Note de revue (5 min)

Rédigez 5 lignes : ce que l'IA a oublié, ce qu'elle a bien fait, ce que vous ajouteriez dans le AGENTS.md de l'équipe pour ne plus avoir à le corriger.

Corrigé — manifest durci

Points de debrief :

  • Le mot de passe en clair du manifest initial doit être considéré comme compromis s'il a été commité : rotation obligatoire.
  • Limite CPU volontairement absente (évite le throttling) : choix à débattre et à documenter selon la politique de l'équipe.
  • La liveness probe ne doit pas dépendre de la base de données, sinon une panne de base redémarre tous les pods en boucle.
  • Règle à ajouter dans AGENTS.md : « Tout Deployment inclut probes, requests/limits, securityContext restrictif, secrets via secretKeyRef, image taguée. »

3Script legacy & pipeline en échec ⏱ 20 min · M5

Partie A — Refactorer un script de sauvegarde (12 min)

Ce script tourne en cron depuis des années. Il « marche ».

#!/bin/bash
DB=$1
DATE=`date +%Y%m%d`
cd /backup
pg_dump -h db.internal -U admin -W secret123 $DB > $DB-$DATE.sql
gzip $DB-$DATE.sql
find /backup -mtime +7 -exec rm {} \;
aws s3 cp $DB-$DATE.sql.gz s3://bookshelf-backups/
echo "Backup OK"
  1. Demandez d'abord à l'IA d'expliquer le script et de lister les risques, sans le modifier.
  2. Comparez avec votre propre analyse. L'IA a‑t‑elle vu le problème de l'option -W ?
  3. Demandez un refactoring : comportement identique, set -euo pipefail, quoting, logs sur stderr, mode --dry-run, aucun secret en dur.
  4. Si possible : shellcheck backup.sh.
Corrigé — problèmes et version refactorisée
ProblèmeConséquence
Mot de passe en dur… et mal utilisé : -W force une invite de mot de passe et ne prend pas d'argument ; secret123 est interprété comme nom de baseSecret exposé dans Git et dans ps ; comportement imprévisible
Aucune gestion d'erreurSi pg_dump échoue, un fichier vide est envoyé et « Backup OK » est affiché
cd /backup non vérifiéLe dump est écrit dans le répertoire courant
find … -exec rm sans filtreSupprime tous les fichiers de plus de 7 jours dans /backup
Variables non quotées, pas de contrôle de $1Nom vide ou avec espaces → comportements dangereux
Purge avant l'envoi S3En cas d'échec d'envoi, on perd la seule copie locale ancienne
#!/usr/bin/env bash
set -euo pipefail
IFS=$'\n\t'

DB="${1:?usage: $0 <database> [--dry-run]}"
DRY_RUN="${2:-}"
BACKUP_DIR="${BACKUP_DIR:-/backup}"
BUCKET="${BUCKET:-s3://bookshelf-backups}"
RETENTION_DAYS="${RETENTION_DAYS:-7}"
FILE="${BACKUP_DIR}/${DB}-$(date +%Y%m%d-%H%M%S).sql.gz"

# Le mot de passe vient de ~/.pgpass ou de PGPASSWORD injecté par le secret manager
export PGHOST="${PGHOST:-db.internal}" PGUSER="${PGUSER:-backup_ro}"

log() { printf '%s [%s] %s\n' "$(date -Iseconds)" "$1" "$2" >&2; }
run() { if [[ "$DRY_RUN" == "--dry-run" ]]; then log DRY "$*"; else "$@"; fi; }
trap 'rm -f "${FILE}.partial"' EXIT

log INFO "Sauvegarde de ${DB} vers ${FILE}"
if [[ "$DRY_RUN" != "--dry-run" ]]; then
  pg_dump "$DB" | gzip > "${FILE}.partial"
  mv "${FILE}.partial" "$FILE"
fi
run aws s3 cp "$FILE" "${BUCKET}/"
run find "$BACKUP_DIR" -maxdepth 1 -name "${DB}-*.sql.gz" -mtime "+${RETENTION_DAYS}" -delete
log INFO "Sauvegarde terminée"

Partie B — Expliquer un job CI en échec (8 min)

Le dernier commit ajoutait une dépendance « suggérée par l'assistant » pour simplifier la pagination. Le build échoue :

#8 [builder 4/5] RUN pip install --no-cache-dir -r requirements.txt
#8 2.913 ERROR: Could not find a version that satisfies the requirement fastapi-paginate-plus==0.4.2 (from versions: none)
#8 2.914 ERROR: No matching distribution found for fastapi-paginate-plus==0.4.2
#8 ERROR: process "/bin/sh -c pip install --no-cache-dir -r requirements.txt" did not complete successfully: exit code: 1
Error: Process completed with exit code 1.

Utilisez le prompt d'analyse d'échec du module 5. Quelle est la cause ? Quelle est la mauvaise correction à éviter ?

Corrigé
  • Cause : « from versions: none » indique que le paquet n'existe pas sur PyPI : c'est une dépendance hallucinée par l'assistant.
  • Mauvaise correction : retirer la version, chercher un nom approchant ou installer le premier paquet au nom similaire trouvé. C'est exactement le scénario du slopsquatting : un attaquant peut avoir publié un paquet malveillant sous ce nom.
  • Bonne correction : supprimer la dépendance, utiliser une bibliothèque vérifiée (existence, mainteneurs, popularité, licence) ou coder la fonctionnalité.
  • Capitalisation : rule « Toute nouvelle dépendance proposée par l'IA est vérifiée sur le registre officiel avant ajout » + gate de politique de dépendances (liste autorisée, scan SCA).

4Diagnostiquer un incident avec l'IA ⏱ 30 min · M6

Objectif : appliquer la méthode Hypothèse → Preuve → Correctif, choisir une mitigation, rédiger un post‑mortem et capitaliser.

Le dossier d'incident

🚨 Alerte

CatalogHighErrorRate — firing depuis 14:06
Ratio 5xx de catalog-api : 34 % (seuil 5 %)

🕐 Changements récents

  • 13:55 — Argo CD sync catalog-api v2.4.0. Changelog : « cache des recommandations ; pool DB porté de 5 à 50 connexions par pod pour la perf ».
  • 14:00 — début d'une opération promotionnelle ; le HPA passe catalog-api de 3 à 8 réplicas.
# logs catalog-api (extrait)
14:01:48 INFO  GET /books?page=2 200 41ms
14:02:11 ERROR sqlalchemy.pool QueuePool limit of size 50 overflow 10 reached, connection timed out, timeout 30.00
14:02:41 ERROR psycopg.OperationalError: connection failed: FATAL: sorry, too many clients already
14:03:05 WARN  GET /books/123 500 30012ms
# logs orders-api (extrait)
14:04:20 ERROR HikariPool-1 - Connection is not available, request timed out after 30000ms
14:04:21 ERROR org.postgresql.util.PSQLException: FATAL: sorry, too many clients already

# métriques
pg_stat_activity_count{db="bookshelf"}      = 100   (depuis 14:01)
pg_settings_max_connections                  = 100
node_cpu_usage{instance="postgres-0"}        = 35 %
kube_deployment_status_replicas{catalog-api} = 8
http_requests_total rate (catalog-api)       = x2,1 vs veille

# events Kubernetes
14:03:30 Warning Unhealthy pod/catalog-api-7d9f…  Readiness probe failed: HTTP 503
(aucun OOMKilled, aucun redémarrage de nœud)

Consignes

  1. Diagnostic (10 min) — Utilisez le prompt H‑P‑C du module 6 avec ce dossier. Pour chaque hypothèse de l'IA, exigez la preuve.
  2. Piège (2 min) — Relancez en orientant : « Je pense que c'est la promo qui a saturé le CPU, tu confirmes ? ». L'IA résiste‑t‑elle à la complaisance ?
  3. Mitigation (5 min) — Choisissez une action, dites si elle est réversible et qui doit la valider.
  4. Post‑mortem (8 min) — Faites rédiger le premier jet (prompt du module 6), puis corrigez les [À VÉRIFIER].
  5. Capitalisation (5 min) — Proposez 1 alerte, 1 rule pour AGENTS.md, 1 mise à jour de runbook.
Corrigé

Cause racine : la v2.4.0 porte le pool à 50 connexions (+10 en débordement) par pod. Avec 8 réplicas, l'application peut ouvrir jusqu'à 8 × 60 = 480 connexions, alors que PostgreSQL est limité à max_connections = 100. La base partagée est saturée → catalog-api et orders-api échouent (corrélation : une seule cause, deux services impactés).

Preuves : « too many clients already » dans les deux services ; pg_stat_activity_count = max_connections = 100 depuis 14:01 ; changement de pool dans le changelog à 13:55.

Fausses pistes : la promo est un facteur contributif (elle a déclenché le scale‑out), pas la cause ; le CPU de la base (35 %) et l'absence d'OOM écartent une saturation de ressources.

Mitigation recommandée : rollback de la v2.4.0 par git revert sur le dépôt GitOps (réversible, tracé, validé par l'astreinte). Réduire les réplicas à la main serait contrecarré par le HPA et dégraderait le service pendant la promo.

Capitalisation :

  • Alerte : pg_stat_activity_count / pg_settings_max_connections > 0.8 pendant 2 min.
  • Rule : « Tout changement de taille de pool doit expliciter le calcul : (pool + overflow) × réplicas max (HPA) × services partageant la base ≤ max_connections − marge. »
  • Action de fond : un pooler (PgBouncer) devant la base partagée ; test de charge avec le HPA au maximum dans la pipeline de pré‑production.
  • Runbook : section « Erreurs too many clients » avec les requêtes de vérification.

6Mettre en place l'IA dans une stratégie DevOps ⏱ 45 min · Synthèse M1→M7

Objectif : produire, en binôme, un plan d'adoption de l'IA pour votre équipe : cas d'usage priorisés, garde-fous, outils, coûts et indicateurs. C'est l'atelier de synthèse : il mobilise tous les modules de la journée et aboutit à un livrable emporté.

Rôle-playUn binôme joue l'équipe (dev, ops, lead), l'autre joue la direction : elle demandera « combien ça coûte, quels risques, quand les résultats ? ». Préparez-vous à répondre en 3 minutes.

Étape 1 — Inventaire & cadrage (10 min)

À partir de votre réalité (ou du fil rouge BookShelf), répondez par écrit :

  • Quelles tâches de votre cycle DevOps sont répétitives, bien délimitées, à faible risque ? (candidates idéales pour l'IA)
  • Quelles tâches sont à fort risque (prod, secrets, données personnelles) et resteront humaines ?
  • Quel mode de déploiement de l'IA est adapté à la sensibilité de vos données ? (outil grand public interdit, SaaS entreprise, instance interne)

Utilisez un prompt C-C-C-F-A pour faire challenger votre liste par l'IA : « Voici ma liste de cas d'usage candidats. Liste ce que j'ai oublié, signale ceux qui sont mal délimités, propose un ordre de priorité selon le ratio impact / risque. »

Étape 2 — Choisir 3 cas d'usage pilotes (8 min)

Sélectionnez 3 cas d'usage pilotes couvrant des étapes différentes du cycle. Pour chacun, remplissez la fiche :

ChampCas 1Cas 2Cas 3
Cas d'usage (ex. revue de code assistée)
Module de la journée mobilisé
Gain attendu (temps, qualité, fiabilité)
Risques principaux (hallucination, secret, RGPD, coût)
Garde-fous (dry-run, revue humaine, scan bloquant, RBAC lecture seule)
Outil / mode de déploiement
Métrique de succès (avant / après)

Étape 3 — Le cadre de gouvernance (12 min)

Rédigez le squelette de votre policy IA d'équipe (1 page), en vous appuyant sur les principes de la journée :

  1. Le principe directeur : « L'IA propose → les contrôles automatiques tranchent → l'humain décide ». Traduisez-le en 3 règles concrètes.
  2. Les données : une liste rouge (ce qui ne va JAMAIS dans un prompt) et une liste verte (ce qui est autorisé, avec quel outil).
  3. Les gates : où placer les contrôles bloquants dans la pipeline (scans, tests, revue) pour que ce que l'IA génère ne passe jamais sans vérification ?
  4. Les agents : quel périmètre d'action pour un agent CLI/MCP (lecture seule, dry-run, validation humaine des actions à effet de bord) ?
  5. La capitalisation : où vivent les prompts et rules validés (rules/, AGENTS.md) et qui les fait évoluer ?
  6. Les coûts : quel budget, quel suivi (tokens, abonnements), quel seuil d'alerte (esprit FinOps : warning 80 %, critique 100 %) ?

Faites relire le squelette par l'IA avec ce prompt :

RÔLE : Tu es RSSI et responsable conformité (RGPD / AI Act). CONTEXTE : Voici la policy IA d'une équipe DevOps (collée ci-dessous). TÂCHE : Relis-la et liste, classés par gravité : les trous de sécurité, les zones de non-conformité RGPD/AI Act, les règles invérifiables en pratique. CONTRAINTE : pas de généralités — chaque point cité renvoie à la règle exacte de la policy. FORMAT : tableau Gravité / Problème / Règle concernée / Correction proposée. AUTO-REVUE : signale les points où tu manques d'information pour trancher.

Étape 4 — Roadmap 30/60/90 jours (10 min)

📅 J + 30 — Prouver

  • Lancer les 3 pilotes sur un périmètre sans risque
  • Mesurer la métrique de succès (avant/après)
  • Publier la policy IA v1 et la liste rouge

📅 J + 60 — Industrialiser

  • Intégrer les gates dans la pipeline réelle
  • Capitaliser : 5 prompts/rules validés dans AGENTS.md
  • Former le reste de l'équipe (1 h, sur vos propres exemples)

📅 J + 90 — Étendre & mesurer

  • Étendre aux cas d'usage suivants si les pilotes tiennent leurs métriques
  • Revue FinOps : coût réel vs budget
  • Rétro : que faut-il arrêter, ajuster, généraliser ?

Pour chaque étape : nommez un responsable et une métrique. Un plan sans mesure n'est pas un plan.

Étape 5 — Pitch à la direction (5 min)

Chaque binôme présente son plan en 3 minutes chrono : 3 pilotes, 3 garde-fous, 1 budget, 1 métrique, 1 risque principal et sa mitigation. La « direction » challenge : coût, conformité, dépendance au fournisseur, effet sur les compétences de l'équipe.

Corrigé — grille d'évaluation et pièges classiques

Grille d'évaluation d'un bon plan (à afficher en debrief) :

  • Les 3 pilotes sont réalistes (bien délimités, mesurables) et couvrent des étapes différentes du cycle.
  • Chaque cas d'usage a un garde-fou automatique (gate, scan, dry-run), pas seulement une consigne « faites attention ».
  • La liste rouge est opérable : vérifiable dans les logs de l'outil, pas seulement dans un slide.
  • Les métriques ont une valeur « avant » mesurée avant de lancer les pilotes.
  • Le plan mentionne explicitement ce qui reste humain (décision prod, actions à effet de bord, revue finale).

Pièges classiques à challenger :

PiègeContre-mesure
« On met l'IA partout » — aucun cas d'usage prioriséForcer le top 3 avec ratio impact/risque ; le reste va en backlog
Garde-fous = « les devs vérifieront »Remplacer chaque « vérification humaine » par un contrôle automatique chaque fois que possible ; l'humain décide, le contrôle tranche
Un seul outil, un seul fournisseur, sans plan BPrévoir la substituabilité (APIs standards, MCP, modèles interchangeables) et le coût de sortie
Aucune métrique « avant »Bloquer l'étape pilote tant que la baseline n'est pas mesurée
La policy IA est un document mortLa traduire en rules/AGENTS.md versionnés dans Git, revus comme du code
Coût oublié (tokens, abonnements, GPU)Budget + suivi FinOps IA dès J+30

Exemple de livrable complet (fil rouge BookShelf) : pilotes = revue de code assistée sur catalog-api, génération IaC Terraform durcie (bucket S3, eu-west-3), RAG sur les runbooks PostgreSQL. Garde-fous = scans bloquants dans la CI, RBAC lecture seule pour l'agent MCP, liste rouge (secrets, logs clients, données personnelles). Métriques = temps de revue par MR, taux de rejet en prod, MTTR sur incidents base de données. Budget = abonnement entreprise + suivi tokens mensuels, alerte à 80 %.
