2MCP et la sécurité des agents

Le Model Context Protocol (MCP) est un standard ouvert, lancé par Anthropic fin 2024 et adopté depuis par la plupart des éditeurs, qui normalise la connexion d'un assistant à des outils et des sources de données (Git, Kubernetes, tickets, monitoring, bases…). C'est « l'USB‑C » des agents.

Les 5 garde‑fous

Garde‑fouPrincipeMise en œuvre
🔑 Moindre privilègeUniquement les droits nécessaires.Serveur MCP en lecture seule, RBAC Kubernetes view, token à portée limitée.
📦 PérimètreBornage explicite.Un namespace / un dépôt de test ; jamais la production en écriture.
🧪 Dry‑runProposer avant d'appliquer.Toute écriture est présentée pour validation ; --dry-run d'abord.
📝 TraçabilitéTout est journalisé.Prompt, outils appelés, proposition, décision humaine, qui / quand.
↩️ RéversibilitéTout est annulable.Actions via Git (PR GitOps → git revert), snapshots.
🚫 Serveurs MCP tiers = code tiersUn serveur MCP s'exécute avec vos identifiants. N'installer que des serveurs de sources fiables, épinglés en version, et revus comme n'importe quelle dépendance. Les descriptions d'outils et les données lues (tickets, pages web, logs) peuvent contenir des injections de prompt.

4Gouvernance : RGPD et AI Act

🇪🇺 RGPD — dès qu'il y a des données personnelles

  • Base légale pour tout traitement (art. 6).
  • Minimisation (art. 5) : n'envoyer que le nécessaire, anonymiser / pseudonymiser.
  • Transferts hors UE encadrés.
  • Une IP, un e‑mail, un identifiant de session dans un log sont des données personnelles.

Ressources : cnil.fr (dossier IA)

⚖️ AI Act — Règlement (UE) 2024/1689

Classe les usages par niveau de risque :

  • 🟥 Inacceptable : interdit (ex. notation sociale).
  • 🟧 Élevé : obligations strictes (ex. IA décidant de l'accès à un service essentiel, RH).
  • 🟨 Limité : transparence (ex. chatbot : dire que c'est une IA).
  • 🟩 Minimal : pas d'obligation spécifique (ex. assistant de code).

Classe de donnéeExemplesOutils autorisés
🟢 PubliqueDoc open source, questions génériquesTout outil, y compris grand public
🔵 InterneCode applicatif, manifests sans secret, runbooksOutils entreprise contractualisés (pas d'entraînement sur vos données)
🟠 ConfidentielleLogs de prod, données clients, architecture sécuritéOutil maîtrisé (cloud privé / self‑hosted) ou anonymisation préalable
🔴 SecrèteSecrets, clés, mots de passe, kubeconfig adminJamais dans un prompt
Contre le Shadow AIInterdire sans proposer d'alternative pousse les usages dans l'ombre. Une politique efficace = des outils autorisés et pratiques + des règles simples + de la formation.

6Considérations éthiques

🧑‍⚖️ Responsabilité

Celui qui commite le code en est responsable, quel que soit son auteur réel. « C'est l'IA qui l'a écrit » n'est pas une excuse.

🔍 Transparence

Signaler les contenus générés (PR, docs, communications) quand c'est pertinent ; ne pas présenter une hypothèse IA comme un fait.

©️ Propriété intellectuelle

Risque de reproduction de code sous licence. Activer les filtres de correspondance avec du code public quand l'outil le propose ; scanner les licences.

⚖️ Biais

Les modèles reflètent leurs données d'entraînement : vigilance sur tout usage touchant des personnes (tri de CV, priorisation de tickets clients…).

🎓 Compétences

Risque de perte de savoir‑faire, surtout pour les juniors. Garder des moments « sans IA », exiger de comprendre ce qu'on commite.

🌱 Impact environnemental

Entraînement et inférence consomment énergie et eau. Choisir le plus petit modèle suffisant, éviter les appels inutiles.

Lancer un mini‑débat (3 min) : « Faut‑il indiquer dans les messages de commit qu'un code a été généré par IA ? » Il n'y a pas de bonne réponse universelle ; l'important est que l'équipe décide et l'écrive dans sa politique.

7Maîtriser les coûts (FinOps de l'IA)

💶 Comment on paie

  • SaaS : licence par utilisateur et/ou tokens d'entrée et de sortie (la sortie coûte généralement plus cher).
  • Self‑hosted : coût fixe (GPU, équipe) indépendant du volume → rentable au‑delà d'un seuil de bascule.
  • Coût caché : le contexte. Chaque message renvoie tout l'historique ; un agent qui lit un dépôt entier consomme beaucoup.

🛠️ Leviers

  • Le bon modèle pour la bonne tâche (petit modèle pour classer, gros pour raisonner).
  • Contexte concis, conversations courtes, cache de prompt.
  • Quotas, budgets et alertes par équipe / projet.
  • Observer chaque appel (coût, latence, modèle) avec un outil comme Langfuse.
  • Mesurer la valeur (DORA, temps gagné), pas seulement la dépense.

8Tendances à suivre

🤖 Agents de code autonomes

De l'issue à la PR : l'agent planifie, code, lance les tests, ouvre la PR. L'humain devient relecteur et architecte.

🔌 Standards ouverts

MCP (outils), protocoles agent‑à‑agent, AGENTS.md, Agent Skills : le contexte devient portable entre outils.

🧑‍🚒 « AI SRE »

Agents d'investigation d'incident intégrés aux plateformes d'observabilité et d'astreinte.

📐 Spec‑driven development

Écrire des spécifications précises que l'agent implémente ; la spec devient l'artefact principal.

🧱 Platform engineering + IA

Golden paths, portails développeurs et garde‑fous intégrés fournis par l'équipe plateforme… y compris pour l'IA.

🧪 Évaluations en CI

Tester les prompts et les agents comme du code : jeux d'évaluation, non‑régression, observabilité des LLM (LLMOps).

🇪🇺 Souveraineté

Modèles ouverts performants, clouds européens, exigences réglementaires : montée des déploiements maîtrisés.

📉 Petits modèles

Modèles compacts spécialisés, moins chers, exécutables localement pour les tâches simples.

9Par où commencer quand on est DevOps

L'IA est surtout utile pour ce qui est répétitif, textuel et vérifiable. Un plan d'implémentation progressif, du moins risqué au plus audacieux :

#ActionEffortRisque
1Review IA des PR + résumé de PR / changelog automatiqueFaibleFaible
2Analyse des échecs de CI (l'agent lit le log, propose le correctif)FaibleFaible
3Review des terraform plan (ce qui va changer, actions risquées)MoyenFaible
4Rules + hooks + protections de branche + CODEOWNERS (cadrer les agents qui développent)MoyenRéduit le risque
5Assistant d'incident en lecture seule (runbooks, dashboards, derniers déploiements)MoyenMoyen
6Actions automatiques (remédiation, déploiement)ÉlevéÉlevé

🛠️ Exemples par domaine

  • IaC : générer Terraform/Helm/Dockerfiles, expliquer un plan, détecter les dérives.
  • Sécurité : prioriser les alertes SAST/scan, proposer des correctifs, revue des permissions IAM/RBAC.
  • Observabilité : résumer un incident, rédiger les post-mortems, améliorer les requêtes PromQL/LogQL.
  • Doc : runbooks, schémas d'architecture, ADR, assistant interne sur la doc.

🧭 Principes

  • Commencer en lecture seule : l'IA propose, l'humain applique.
  • Droits minimaux ; jamais de prod ni de secrets sans validation.
  • Les contrôles critiques restent déterministes (tests, policies as code OPA/Conftest, CI) — l'IA en complément.
  • Humain dans la boucle pour prod, données, accès.
  • Mesurer (temps de review, taux de fausses alertes) avant d'étendre.
