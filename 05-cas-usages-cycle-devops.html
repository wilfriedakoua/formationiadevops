Cas d'usage de l'IA dans le cycle DevOps

Étape par étape, de la user story au déploiement : ce que l'IA fait bien, ce qu'elle oublie, et le contrôle à garder à chaque fois.

🎯 Objectifs du module

  • Identifier des cas d'usage concrets à chaque étape de la boucle DevOps.
  • Appliquer la boucle de production assistée : générer → valider → durcir → commiter.
  • Connaître les oublis typiques de l'IA sur Kubernetes, Terraform, Bash et CI/CD.
  • Concevoir une pipeline augmentée où l'IA assiste sans décider.
Reprendre les usages notés au tableau en début de M1 et les placer sur la boucle DevOps au fur et à mesure.

1La boucle de production assistée

On ne commite jamais la sortie brute d'un assistant. Elle passe par une boucle :

stateDiagram-v2 direction LR [*] --> Prompt Prompt --> Generation : prompt structuré Generation --> Validation : sortie brute Validation --> Revue : lint, dry-run, tests, scans OK Validation --> Prompt : erreurs Revue --> Durcissement : oublis détectés Durcissement --> Validation Revue --> Commit : critères OK Commit --> [*]
Règle d'orLa sortie IA est une proposition. Le livrable, c'est la proposition validée, relue et durcie. Générer donne la forme ; durcir la rend sûre.

3Plan & Code

📋 Transformer un besoin en user stories

Tu es Product Owner technique. À partir du besoin ci-dessous, rédige 3 à 5 user stories au format « En tant que… je veux… afin de… », chacune avec 3 critères d'acceptation Gherkin (Given/When/Then). Signale les ambiguïtés du besoin. <besoin>Les clients doivent être prévenus quand un livre de leur liste de souhaits revient en stock.</besoin>

🧓 Comprendre et refactorer du code hérité

Explique ce script Bash ligne par ligne pour un nouvel arrivant, puis liste les risques (gestion d'erreurs, quoting, idempotence). Ne modifie rien pour l'instant. ```bash [script] ```

Puis, dans un 2e prompt : « Refactorise en gardant le comportement identique, ajoute set -euo pipefail, des messages d'erreur sur stderr et un mode --dry-run. »

🧪 Générer des tests

Demander des tests des cas limites (entrées vides, erreurs réseau, valeurs extrêmes), pas seulement le cas nominal. Vérifier que les tests échouent quand on casse le code (sinon ils ne testent rien).

🔄 Migrer une version

Java 11 → 21, Python 3.8 → 3.12, API Kubernetes dépréciées : l'IA liste les changements cassants et propose les modifications. Toujours confronter à la doc officielle de migration.

5CI/CD : expliquer un échec de pipeline

C'est l'un des cas d'usage au meilleur retour sur investissement : on colle le log, l'IA propose des hypothèses classées avec la preuve à chercher.

$ docker push registry.example.com//catalog-api:3f2a1c
invalid reference format
ERROR: Job failed: exit code 1
Tu es ingénieur CI/CD. Voici le log d'un job GitLab CI en échec et l'extrait du .gitlab-ci.yml correspondant. Donne 3 hypothèses classées par probabilité. Pour chacune : la preuve dans le log qui la soutient, la vérification à faire, et le correctif. Ne propose PAS de désactiver une étape ni d'ajouter allow_failure. <log>...</log> <ci>...</ci>

➡️ Réponse attendue : le double // trahit une variable vide ($CI_PROJECT_NAMESPACE ou $IMAGE_PREFIX non définie dans ce contexte, ex. pipeline de MR depuis un fork, variable protégée non exposée).

⚠️ PiègeSous pression, l'IA (comme l'humain) propose volontiers allow_failure: true ou un .trivyignore large. Un gate désactivé sans trace est une dette de sécurité invisible : toute exception doit être explicite, datée et justifiée.

6Sécurité : trier un rapport de scan

Un scan Trivy peut sortir des centaines de lignes. Le gate filtre (HIGH/CRITICAL bloquant) ; l'IA aide à prioriser le reste.

Voici le rapport Trivy (JSON) de l'image catalog-api. Contexte : API interne, exposée uniquement derrière l'ingress, Python 3.12. 1. Regroupe les vulnérabilités par paquet. 2. Sépare : corrigeable (fixed version dispo) / non corrigeable. 3. Pour les corrigeables, donne la ligne à modifier (requirements.txt ou image de base). 4. Signale celles qui touchent un composant réellement utilisé à l'exécution. Ne recommande aucune exception sans la marquer « À VALIDER PAR UN HUMAIN ».

🤖 Revue de PR assistée

Commentaire automatique : résumé du changement, points de vigilance sécurité, tests manquants. Non bloquant ; les gates et l'approbation humaine restent décisionnaires.

🧭 Threat modeling

« Voici le schéma d'architecture. Applique STRIDE et liste les 10 menaces principales avec une mesure pour chacune. » Bon point de départ pour un atelier sécurité.

7La pipeline augmentée

L'IA s'installe autour de la pipeline, jamais comme maillon de décision.

flowchart TB subgraph DET["Chaîne de décision déterministe"] direction LR T["Tests"] --> SA["Lint · SAST · Gitleaks"] --> B["Build"] --> SC["Trivy"] --> P["Publish"] --> G["PR GitOps"] --> H["🧑 Approbation"] end subgraph IA["Assistance IA (non bloquante)"] direction LR I1["Générer / expliquer le YAML"] I2["Expliquer un job rouge"] I3["Résumer le scan"] I4["Commenter la PR"] end IA -.->|"propose, n'impose pas"| DET style DET fill:#f0fdf4,stroke:#16a34a style IA fill:#eff6ff,stroke:#2563eb

Exemple : un job de revue IA non bloquant (GitLab CI)

ai-review:
  stage: review
  image: python:3.12-slim
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
  script:
    - pip install -q -r tools/requirements.txt
    - python tools/ai_review.py --diff "$CI_MERGE_REQUEST_DIFF_BASE_SHA" --post-comment
  allow_failure: true   # l'IA commente, elle ne bloque jamais
  timeout: 5m
💡 Bonnes pratiquesClé d'API dans une variable CI masquée et protégée ; ne pas envoyer le diff à un service externe si le dépôt est confidentiel ; journaliser coût et latence de chaque appel (cf. M7).

8Qui relit quoi ? Dev humain, dev IA

Quand l'humain développe, l'IA relecte

flowchart LR D["🧑 Dev humain
écrit le code"] --> H["🪝 Hook local
/review, lint, tests"] H --> PR["Pull Request"] PR --> CI["✅ CI : tests · linter
SAST · scan secrets"] CI --> AR["🤖 Review agent
lit le diff + rules"] AR --> RH["🧑 Relecture humaine"] RH --> DEP["🚀 Déploiement"]

La rule de review porte la checklist de l'équipe (sécurité, conventions, tests présents, pas de secrets) ; le hook garantit ce que la rule ne peut que demander ; un skill peut décrire le « go/no-go » avant déploiement (migrations, variables, changelog).

Quand l'IA développe : déplacer la confiance du jugement vers la preuve

Si le même modèle écrit et relit, il a les mêmes angles morts : il trouve son propre code raisonnable. Les garde-fous ne reposent pas sur « l'IA qui vérifie l'IA » :

🔒 Contrôles indépendants

  • Tests, typage strict, linter, SAST, scan de dépendances, build en CI — déterministes, qu'un humain ou une IA ait écrit le code.
  • Critères d'acceptation (voire les tests) écrits ou relus par l'humain, l'IA code pour les faire passer.
  • Si review IA : un autre modèle, un contexte vierge (diff + rules seulement), un rôle adversarial (« trouve ce qui peut casser »).

🧱 Périmètre & focus humain

  • Branches séparées, jamais main ; protection de branche : merge impossible sans CI verte ; pas d'accès prod ni secrets.
  • CODEOWNERS : validation humaine obligatoire sur les zones sensibles (auth, paiement, données perso, migrations, infra).
  • Déploiement progressif (canary, feature flags), monitoring, rollback rapide : un bug passera parfois.
À retenirOn ne demande pas à l'IA « es-tu sûre ? » : on exige que le code passe des tests et des contrôles qu'elle ne peut pas contourner par sa propre opinion.

9Mesurer l'apport réel

📊 Métriques DORA

Le délai de mise en production baisse‑t‑il ? Le taux d'échec des changements reste‑t‑il stable ?

⏱️ Temps gagné

Sur des tâches ciblées : rédaction de runbook, diagnostic de pipeline, migration.

✅ Taux d'acceptation

Part des suggestions conservées après revue, et nombre de corrections nécessaires.

😊 Expérience développeur

Enquêtes régulières : charge cognitive, satisfaction, sentiment de flow.

⚠️ À ne pas mesurer seulLe nombre de lignes générées ou le nombre de prompts : ils encouragent les gros lots, donc l'instabilité.
