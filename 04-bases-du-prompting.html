Les bases du prompting

Passer de « demander à un chatbot » à « piloter un assistant » : structurer, contraindre, décomposer, itérer — et capitaliser ses prompts comme du code.

🎯 Objectifs du module

  • Structurer un prompt avec les 5 composants : Rôle, Contexte, Contraintes, Format, Auto‑revue.
  • Utiliser les techniques clés : exemples, décomposition, questions préalables, itération.
  • Appliquer l'hygiène de contexte (et ne pas fuiter de secrets).
  • Capitaliser au niveau de l'équipe : AGENTS.md, rules, bibliothèque de prompts.

1Pourquoi un prompt DevOps n'est pas un prompt de chatbot

Sans contraintes, le modèle choisit la réponse la plus fréquente dans ses données d'entraînement — rarement la plus sûre pour la production.

Crée-moi un bucket S3 avec Terraform.

➡️ Résultat typique : région par défaut, pas de chiffrement explicite, pas de versioning, pas de blocage d'accès public, parfois une syntaxe de provider ancienne.

Tu es ingénieur plateforme AWS. Contexte : projet BookShelf, Terraform >= 1.6, provider AWS v5, région eu-west-3. Crée un bucket S3 pour les artefacts de build. Contraintes : versioning activé, chiffrement SSE-KMS, accès public bloqué, tags app=bookshelf et env=dev, ressources séparées (pas de blocs inline dépréciés). Format : un seul fichier main.tf, commentaires en français. À la fin, liste les hypothèses que tu as faites et 2 points à vérifier.
RègleChaque information absente du prompt est une hypothèse implicite que le modèle fera à votre place.

2L'anatomie d'un prompt structuré : R‑C‑C‑F‑A

ComposantQuestionExemple BookShelf
R · RôleQuel point de vue / quelle expertise ?« Tu es SRE senior spécialisé Kubernetes et sécurité. »
C · ContexteQuel projet, quelle stack, quelles versions, quel existant ?« Service catalog-api, FastAPI, port 8000, santé sur /health, Kubernetes 1.30, namespace bookshelf. »
C · ContraintesQu'est‑ce qui n'est pas négociable ?« Probes, requests/limits, non‑root, image taguée (pas latest), aucun secret en clair. »
F · FormatQuelle forme de sortie ?« Un seul fichier YAML k8s/deployment.yaml, sans explication autour. »
A · Auto‑revueQuel contrôle l'assistant fait‑il sur sa propre réponse ?« Termine par la liste des hypothèses et des points à durcir. »

Gabarit réutilisable

RÔLE : Tu es [expertise] qui [objectif].
CONTEXTE : [projet, stack, versions, environnement, existant pertinent]
TÂCHE : [ce que tu dois produire, en une phrase]
CONTRAINTES :
- [règle non négociable 1]
- [règle non négociable 2]
FORMAT : [type de fichier, structure, langue, longueur]
AUTO-REVUE : Avant de répondre, vérifie [critères].
           Termine par : hypothèses prises, risques, tests à lancer.
D'autres équipes utilisent des acronymes comme CO‑STAR, RACE ou CRISPE. L'acronyme importe peu : ce qui compte, c'est la discipline contexte + contraintes + format + auto‑revue.

3Hygiène de contexte

Plus de contexte ne veut pas dire meilleure réponse. Le bon contexte est pertinent, à jour, concis.

✅ À faire

  • Ne fournir que les fichiers et extraits utiles.
  • Consignes critiques en tête, rappel du format en fin.
  • Préciser les versions (K8s, Terraform, provider, langage).
  • Une conversation = un sujet ; repartir à zéro quand on change de sujet.
  • Fournir la doc à jour quand la techno est récente.

🚫 À éviter

  • Coller des secrets, tokens, mots de passe, kubeconfig.
  • Coller des données personnelles (IP, e‑mails, noms) sans anonymisation.
  • Joindre tout le dépôt « au cas où ».
  • Laisser de la doc obsolète ou contradictoire dans le contexte.
  • Des conversations de 200 messages qui dérivent.
🔐 Réflexe sécuritéAvant de coller un log ou une config : « Est‑ce que je l'enverrais par e‑mail à un prestataire externe ? » Si non, anonymisez ou utilisez un outil maîtrisé. Pensez aux outils de détection de secrets (Gitleaks) avant tout envoi.

4Les briques du contexte d'équipe

Pour briefer l'IA sur un projet, six briques à connaître. Elles vivent dans le dépôt Git : versionnées, relues en PR, partagées par toute l'équipe.

📜 Rules

Consignes permanentes, lues à chaque session — le règlement intérieur du projet. « Jamais de secret en clair. Toujours des requests/limits. »

🎓 Skills

Savoir-faire réutilisable (SKILL.md), chargé seulement quand la tâche correspond. « Générer un manifest K8s durci. »

⌨️ Commands

Prompts enregistrés, déclenchés à la demande : /review, /test, /deploy.

🪝 Hooks

Actions automatiques déterministes (formatter, bloquer un commit) — l'IA ne peut pas les ignorer.

🤖 Agents

Sous-assistants spécialisés à droits limités (reviewer sécurité en lecture seule…).

🔌 MCP

Connexion aux outils externes : Git, cluster, monitoring. Détails et sécurité en M7.

Où placer le contrôle ?Vrai en permanence → rule · doit être garanti → hook, CI ou permissions · lancé par vous → command · procédure que l'IA doit reconnaître seule → skill. Commencer par les rules ; ajouter le reste quand un besoin concret apparaît.

5Comment configurer son repo pour l'IA

Ces fichiers ne changent rien au fonctionnement du code : ils briefer l'IA quand elle travaille sur le projet — et documentent au passage les conventions pour les humains. À la racine du dépôt, on trouve typiquement :

mon-projet/
├── AGENTS.md              # règles : lues à chaque session
├── opencode.json          # config OpenCode (MCP, permissions...)
├── .mcp.json              # connexions aux outils externes
├── .opencode/             # OpenCode (chaque outil a son équivalent)
│   ├── hooks/             # plugins (actions automatiques)
│   ├── commands/          # review.md, test.md, deploy.md
│   └── skills/
│       ├── terraform-review/   # SKILL.md + scripts/
│       └── security-audit/     # SKILL.md + scripts/
├── agents/
│   ├── security-reviewer.md    # sous-agent lecture seule
│   └── devops-expert.md
├── scripts/               # deploy.sh, security-check.sh
├── src/ · tests/ · terraform/
└── .gitlab-ci.yml         # les gates, indépendants de l'IA
⚠️ Proposition d'organisationChaque outil IA a ses propres conventions : Claude Code reconnaît nativement .claude/commands/ et .claude/skills/, d'autres outils nécessitent une configuration différente. Le contenu reste portable, seuls les emplacements changent.

6Exemple : une rule

AGENTS.md (à la racine du dépôt)

# Project Rules

## Stack
- Python 3.12 / FastAPI, Java 21 / Spring Boot, PostgreSQL 16
- Kubernetes 1.30, Argo CD, Terraform >= 1.6 (provider AWS v5)

## Règles non négociables
- Aucun secret en clair : utiliser des Secrets K8s / un secret manager.
- Images taguées par SHA ou version, jamais `latest`.
- Tout Deployment a : readiness/liveness probes, requests/limits, runAsNonRoot.
- Scripts Bash : `set -euo pipefail`.

## Commandes de vérification
- `kubectl apply --dry-run=server -f k8s/`
- `terraform fmt -check && terraform validate`
- `pytest -q` ; `gitleaks detect` ; `trivy config .`

## Ce que l'assistant ne doit jamais faire
- Exécuter une commande d'écriture sur un cluster de production.
- Modifier la CI pour désactiver un scan.

Même contenu, quel que soit votre assistant

OutilEmplacement
Standard ouvert (tous)AGENTS.md
OpenCodeAGENTS.md, opencode.json
Cursor.cursor/rules/*.mdc
GitHub Copilot.github/copilot-instructions.md
Gemini CLIGEMINI.md
💡 Comment ça marcheQuand l'assistant ouvre le dépôt, il lit ces règles et les applique. Demandez « Crée-moi un Dockerfile pour mon application Python » : il sait déjà — Python 3.12, conventions du projet, pas de secrets, moindre privilège. Vous n'avez pas à répéter ces consignes dans chaque prompt.
RuleConsignes générales, toujours appliquées — contrairement au skill (chargé quand la tâche le nécessite) et à la command (déclenchée explicitement).

7Exemple : un skill et une command

Un skill — skills/terraform-review/SKILL.md

---
name: terraform-review
description: Analyse la sécurité du code
Terraform et identifie les mauvaises
configurations.
---

# Terraform Security Review

## Procédure
1. Identifier les fichiers .tf.
2. Vérifier les configurations IAM.
3. Identifier les ressources exposées
   publiquement.
4. Vérifier le chiffrement des données.
5. Rechercher les secrets en dur.
6. Exécuter terraform validate.
7. Exécuter Checkov si disponible.

## Résultat attendu
Vulnérabilité · fichier et ligne ·
criticité · recommandation de correction.

Format Agent Skills (ouvert) : la description est l'élément clé, c'est elle qui fait charger le skill au bon moment. On y joint scripts, templates de rapports, exemples conformes.

Une command — commands/review.md

Relis le diff de la branche courante selon
AGENTS.md : sécurité, conventions, tests,
secrets. Pour chaque problème : fichier,
ligne, gravité, correction proposée.
Ne modifie aucun fichier.

Un prompt enregistré que vous déclenchez (/review). Chaque outil a son dossier (commands/, .claude/commands/, .cursor/commands/…) — le contenu reste portable.

CommandeFonction
/reviewRéaliser une code review
/testGénérer et exécuter des tests
/deployPréparer un déploiement
/auditAuditer la sécurité
SkillProcédure chargée quand la tâche le nécessite — la description du SKILL.md fait le tri. Demandez « Fais un audit de sécurité de mon infrastructure Terraform » : l'assistant reconnaît la description, charge le skill et suit la procédure.
CommandPrompt enregistré, déclenché explicitement par vous (/review) — contrairement à la rule (toujours appliquée) et au skill (reconnu seul).

8Exemple : un hook

Hook Git — .pre-commit-config.yaml

repos:
  - repo: https://github.com/astral-sh/ruff-pre-commit
    rev: v0.14.0
    hooks:
      - id: ruff
        args: [--fix]
      - id: ruff-format
pip install pre-commit
pre-commit install

À chaque commit (humain ou généré par IA, quel que soit l'outil), les contrôles configurés s'exécutent automatiquement.

Hook d'assistant — OpenCode (plugins)

{ "hooks": { "PostToolUse": [{
  "matcher": "Edit|Write",
  "command": "npm run lint --fix &&
              npx gitleaks detect --redact"
}]}}

OpenCode n'a pas de hooks natifs : on passe par son système de plugins pour déclencher des actions automatiques (formater après une modification, contrôle de sécurité après génération de code…). Exemples de déclencheurs utiles : avant un commit, avant un déploiement.

Pourquoi c'est la brique la plus importanteUn hook est déterministe : il s'exécute quoi qu'il arrive, l'IA ne peut pas l'ignorer — contrairement à une rule, qui n'est qu'une consigne. ⚠️ Un hook Git local peut être contourné (--no-verify) : pour une véritable garantie, imposez aussi les contrôles dans la CI/CD et protégez les branches.

9Exemple : des agents spécialisés

Objectif : déléguer des tâches à plusieurs assistants aux rôles différents, puis consolider.

agents/security-reviewer.md

# Security Reviewer

## Rôle
Tu es un expert en cybersécurité.

## Missions
- Analyser les vulnérabilités.
- Identifier les secrets exposés.
- Vérifier les permissions IAM.
- Analyser les Dockerfiles.

## Restrictions
- Lecture seule.
- Ne jamais modifier les fichiers.
- Ne jamais déployer.

agents/devops-expert.md

# DevOps Expert

## Rôle
Tu es un expert DevOps.

## Missions
- Analyser les pipelines CI/CD.
- Optimiser les Dockerfiles.
- Vérifier les manifests Kubernetes.
- Proposer des améliorations Terraform.

## Restrictions
- Ne jamais déployer en production
  sans autorisation.
💡 Utilisation« Analyse mon projet avant sa mise en production : demande à l'agent DevOps de vérifier les pipelines et à l'agent Security de réaliser un audit. » L'assistant principal délègue aux agents spécialisés, puis consolide les résultats.
⚠️ LimitesUn fichier Markdown décrivant un agent ne suffit pas à l'activer : il faut le déclarer selon le mécanisme de sous-agents de l'outil utilisé (par ex. .claude/agents/ avec ses métadonnées). Toujours des restrictions explicites : lecture seule, pas de déploiement.

10Exemple : connecter l'IA aux outils externes (MCP)

Par défaut, l'assistant ne connaît que les fichiers du dépôt. Le MCP le connecte à vos systèmes : GitLab, Kubernetes, Prometheus, Jira… (cf. M7 pour la sécurité).

.mcp.json — exemple GitLab

{
  "mcpServers": {
    "gitlab": {
      "command": "npx",
      "args": [
        "-y",
        "@modelcontextprotocol/server-gitlab"
      ],
      "env": {
        "GITLAB_TOKEN": "${GITLAB_TOKEN}"
      }
    }
  }
}

Exemple illustratif : le nom du package et les paramètres doivent correspondre au serveur MCP réellement installé. Le token vient de l'environnement, jamais du fichier.

Ce que ça permet

Une fois connecté, si le serveur expose un outil de consultation des Merge Requests :

Consulte les Merge Requests ouvertes sur mon projet GitLab et identifie celles qui présentent des risques de sécurité.

L'assistant utilise les outils exposés par le serveur MCP pour réaliser l'opération.

⚠️ Rappel sécuritéUn serveur MCP s'exécute avec vos identifiants : sources fiables, versions épinglées, lecture seule par défaut, RBAC côté système visé (détail en M7).
